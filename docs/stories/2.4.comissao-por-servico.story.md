## Story

**As a** dono do salão,
**I want** definir uma comissão diferente para um serviço específico de um profissional,
**so that** serviços com custo de produto ou margem diferente sejam remunerados de forma justa.

## Acceptance Criteria

1. `ComissaoRegra` passa a aceitar escopo por serviço: além da regra geral (`servicoId` nulo), é possível ter regras com `servicoId` preenchido para o mesmo profissional. A unicidade muda de `profissionalId @unique` para `@@unique([profissionalId, servicoId])`. A migração é aditiva — as linhas existentes (uma por profissional, hoje `profissionalId @unique`) continuam válidas como a regra geral (`servicoId = null`); nenhum dado é perdido ou recriado.
2. `src/lib/financeiro.ts` ganha função **pura** que resolve o percentual de um atendimento: regra do serviço se existir para aquele profissional, senão a regra geral do profissional, senão `0`. Coberta por testes (só geral; geral + serviço específico; nem geral nem serviço → 0; serviço específico sem geral).
3. A tela de edição de profissional (`/profissionais`) lista os serviços ativos e permite definir um `%` por serviço, além do `%` geral já existente (Story 1.3). Campo vazio = sem regra específica para aquele serviço (usa a geral).
4. O relatório de comissões (`/comissoes`) detalha, por profissional, a quebra por serviço **quando houver regra específica** para pelo menos um serviço daquele profissional; o total por profissional continua correto (igual à soma das comissões calculadas por atendimento, não a uma média).
5. **Sem regra específica**, o comportamento é idêntico ao Epic 1: comissão = `% geral × total cobrado`. Regressão coberta por teste (todos os testes existentes de `comissaoPorProfissional` continuam passando).
6. `npm run test`, `npm run lint`, `npm run build` verdes.

## Dev Notes

### Contexto (Stories 1.3, 1.8, 2.3)

- `src/lib/financeiro.ts` hoje: `comissao(valorCobrado, percentual)`, `comissaoPorProfissional(atendimentos, percentualPorProfissional)`. `AtendimentoInput` tem só `{ valorCobrado, profissionalId }` — **não** tem `servicoId` ainda. `[Source: src/lib/financeiro.ts]`
- `prisma/schema.prisma` hoje: `ComissaoRegra { id, profissional Profissional @relation(...), profissionalId String @unique, percentual Float, criadoEm }`; `Profissional.comissaoRegra ComissaoRegra?` (1:1). `Agendamento` já tem `servicoId String` (obrigatório, relação com `Servico`) — não precisa de migração no `Agendamento`. `[Source: prisma/schema.prisma]`
- `src/app/(app)/profissionais/actions.ts`: `definirComissao` faz `prisma.$transaction([comissaoRegra.upsert({ where: { profissionalId }, ... }), profissional.update({ data: { comissaoPercentual } })])` — o campo `Profissional.comissaoPercentual` é um **espelho legado** da Story 1.3; `/comissoes` já trata `ComissaoRegra` como fonte canônica (`comissaoRegra?.percentual ?? 0`), então o espelho pode ficar desatualizado sem quebrar nada, mas manter a escrita por consistência com o dado existente. `[Source: src/app/(app)/profissionais/actions.ts]`
- `src/app/(app)/profissionais/ProfissionalRow.tsx`: hoje usa `p.comissaoRegra?.percentual ?? p.comissaoPercentual ?? 0` (singular). `[Source: src/app/(app)/profissionais/ProfissionalRow.tsx]`
- `src/app/(app)/comissoes/page.tsx`: busca `prisma.profissional.findMany({ include: { comissaoRegra: true } })` e monta `percentualPorProfissional[p.id] = p.comissaoRegra?.percentual ?? 0`; a query de atendimentos só seleciona `profissionalId`, `valorCobrado` (precisa passar a selecionar `servicoId` também). `[Source: src/app/(app)/comissoes/page.tsx]`

### Cuidado — unicidade da regra geral (@data-engineer)

SQLite trata cada `NULL` como distinto num índice único, então `@@unique([profissionalId, servicoId])` **não impede**, no nível do banco, duas linhas com o mesmo `profissionalId` e `servicoId = NULL` (duas "regras gerais" pro mesmo profissional). O Prisma resolve a busca (`findUnique`/`upsert` pela chave composta) corretamente com `servicoId: null` porque traduz para `IS NULL` na query — então, **desde que toda escrita passe pelas actions desta story** (`definirComissao` / `definirComissaoServico`, ambas usando a chave composta), a unicidade fica garantida na prática. Não é necessário um `CHECK` ou índice parcial para o escopo desta story; documentar a suposição no Change Log.

### Decisões a tomar (registrar no Change Log)

1. **Substituir `comissaoPorProfissional` ou adicionar `comissaoPorProfissionalComServico` ao lado dela?** Recomendação: adicionar a nova função e migrar `/comissoes` para usá-la nesta story (a antiga fica só nos testes de regressão/Story 1.8, se ainda fizer sentido mantê-la, ou é removida se `/comissoes` era o único consumidor — conferir com `Grep` antes de remover).
2. **Layout da quebra por serviço no relatório:** recomendação — abaixo da linha do profissional (linha "pai"), uma sub-lista/sub-tabela com os serviços que têm regra específica (nome do serviço, qtd, total, comissão). Profissionais sem nenhuma regra específica não ganham essa sub-lista. Ajuste fino de layout é decisão do @dev; sem necessidade de @ux-design-expert para esta story.

### Assunções explícitas

- Regra por serviço é **por profissional** (o mesmo serviço pode ter % diferente para profissionais diferentes) — já é assim que `ComissaoRegra` se relaciona (`profissionalId` na regra).
- A comissão continua calculada sobre o **valor cobrado bruto** nesta story; o toggle bruto/líquido é a Story 2.5 (não implementar aqui).
- Serviço inativo mantém a regra específica já criada (só não aparece na lista de edição para criar uma nova); não é necessário migrar/limpar regras de serviços desativados.

### Edge cases

- Profissional sem nenhuma `ComissaoRegra` (nem geral, nem por serviço) → comissão 0 em todos os atendimentos, sem erro (comportamento já coberto pela Story 1.3/1.8).
- Profissional com regra geral mas sem nenhuma regra por serviço → comportamento idêntico ao Epic 1 (AC 5); sem quebra no relatório.
- Atendimento de um serviço que foi excluído/desativado depois de concluído → `servicoId` no `Agendamento` continua apontando pro serviço (nunca é apagado, só desativado — Story de exclusão de serviço já trata isso); a resolução do percentual funciona normalmente.
- `percentual` fora de 0..100 na regra por serviço → mesmo erro pt-BR da regra geral, não grava.

### Testing

- **Manual:**

  2. Definir comissão específica de 60% para um serviço desse profissional.
