## Story

**As a** cliente que agendou pelo link público,
**I want** também receber o lembrete do meu horário por WhatsApp (quando o salão tiver isso configurado),
**so that** eu veja o lembrete no canal que uso no dia a dia, além do e-mail.

## Acceptance Criteria

1. `src/lib/whatsapp.ts` expõe `enviarWhatsapp({ to, parametros }): Promise<boolean>`, onde `to` é o telefone já normalizado e `parametros` é a lista ordenada de valores do template (`[nome, servicoNome, profissionalNome, dataHoraLabel]`). Sem `WHATSAPP_ACCESS_TOKEN`/`WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_TEMPLATE_NAME` configuradas (todas obrigatórias), retorna `false` imediatamente, **sem tentar a chamada HTTP e sem lançar erro** — mesma degradação graciosa do `enviarEmail` (Story 8.2).
2. `normalizarTelefoneBR(telefone: string): string | null` (em `src/lib/whatsapp.ts`) converte um telefone armazenado no formato livre do cadastro (ex.: `"11999990000"`) para o formato E.164 exigido pela API do WhatsApp (ex.: `"5511999990000"`); telefones que não têm cara de número brasileiro válido (poucos dígitos, etc.) retornam `null` e são tratados como "sem WhatsApp disponível" — sem erro visível.
3. `GET /api/lembretes` (Story 8.2) passa a tentar **os dois canais** na mesma execução, quando elegíveis: e-mail (já existente) e, agora, WhatsApp — quando `enviarWhatsapp` está configurado **e** `normalizarTelefoneBR(cliente.telefone)` não é nulo. `lembreteEnviadoEm` é gravado quando **pelo menos um dos dois canais** teve sucesso nessa execução (ver Dev Notes — trade-off documentado).
4. Sem nenhuma variável de WhatsApp configurada, o comportamento observável da rota é **idêntico** ao da Story 8.2 (só e-mail) — nenhuma mudança de contrato, nenhum erro nem log de "WhatsApp desativado" poluindo a saída normal.
5. A mensagem de WhatsApp usa um **template pré-aprovado** no Meta Business Manager (fora do escopo de código) com exatamente 4 variáveis de corpo, nesta ordem: nome do cliente, nome do serviço, nome do profissional, data/hora formatada. O nome e o idioma do template vêm de `WHATSAPP_TEMPLATE_NAME`/`WHATSAPP_TEMPLATE_LANG` (default `pt_BR`).
6. `.env.example` e `DEPLOY.md` documentam as novas variáveis (`WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_TEMPLATE_NAME`, `WHATSAPP_TEMPLATE_LANG`) e deixam explícito, como passo manual de infraestrutura (mesmo padrão da Story 8.2 pro Cron Job): criar um app WhatsApp Business no Meta Business Manager, obter o token/phone number ID, e criar+aprovar um template com o contrato de 4 variáveis do AC 5.
7. `npm run test`, `npm run lint` e `npm run build` continuam verdes.

## Dev Notes

### Contexto (arquivos relevantes já existentes)

- `src/lib/email.ts` (Story 8.2): `enviarEmail`/`configurado()` são o modelo exato a replicar em `whatsapp.ts` — mesma forma de checar env vars, mesmo `try/catch` que nunca deixa a exceção escapar, mesmo retorno `boolean`. `escapeHtml` não se aplica aqui (a API do WhatsApp usa parâmetros de texto simples de um template, não HTML — a Meta não interpreta markup nos parâmetros). `[Source: src/lib/email.ts]`
- `src/app/api/lembretes/route.ts` (Story 8.2, código atual): o loop de hoje (linhas 35–58) já resolve `servico`/`profissional`/`cliente` via `include`, já calcula `formatarDataHora(ag.inicio)`, e já tem o padrão "`pulados++` no topo quando não elegível, `if (ok) { update + enviados++ }` no fim". Esta story só estende esse mesmo loop pra tentar um segundo canal — não reescreve a rota. `[Source: src/app/api/lembretes/route.ts]`
- `prisma/schema.prisma`: `Cliente.telefone` é `String?` de formato livre (sem validação/máscara em nenhuma tela do projeto até aqui) — por isso a necessidade de `normalizarTelefoneBR` nesta story; nenhuma mudança de schema é necessária (WhatsApp usa o mesmo `telefone` já cadastrado, não um campo novo). `[Source: prisma/schema.prisma]`
- Nenhuma dependência nova de pacote: a Cloud API do WhatsApp é uma API REST simples — `fetch` (global, disponível no runtime Node do Next.js 15) é suficiente, ao contrário do e-mail (SMTP), que exigiu `nodemailer`.

### Cuidado ao rodar os testes antigos de `route.test.ts` sem mockar `@/lib/whatsapp`

Os testes da Story 8.2 usam um `cliente` mockado **sem** campo `telefone` (`{ nome: "Cliente", email: "cliente@teste.com" }`) — por isso `telefoneWhats` sempre resolve `null` neles, `enviarWhatsapp` real nunca é chamado, e nenhuma chamada de rede escapa pro `fetch` de verdade durante os testes, mesmo sem mockar `@/lib/whatsapp` explicitamente nesses casos antigos. **Se qualquer teste (novo ou reaproveitado) adicionar um `telefone` ao mock de cliente sem também mockar `@/lib/email` ou `@/lib/whatsapp`**, o teste vai tentar uma chamada de rede de verdade — sempre mockar os dois módulos nos testes novos da Task 4, como já é o padrão do projeto pra dependências externas.

### Por que gravar `lembreteEnviadoEm` com "pelo menos um canal" (trade-off documentado)

FR38 pede que o lembrete "também" saia por WhatsApp, além do e-mail — o ideal seria rastrear e re-tentar cada canal de forma independente. Isso exigiria uma segunda coluna (`lembreteWhatsappEnviadoEm`, por exemplo) e mais uma migração. Pra manter a story pequena e o schema simples (Article IV — No Invention: não construir rastreamento por canal que ninguém pediu explicitamente), esta fatia trata o "lembrete" como uma coisa só: se pelo menos um canal saiu, o cliente foi lembrado, e a execução seguinte não tenta de novo — mesmo que o outro canal tenha falhado nessa mesma execução. Limitação conhecida: se o e-mail falhar e o WhatsApp funcionar (ou vice-versa) numa execução, o canal que falhou **não** é re-tentado numa próxima execução, porque `lembreteEnviadoEm` já foi gravado. Aceitável porque os dois canais são tentados **na mesma execução**, minimizando a janela de perda, e porque o objetivo de negócio (cliente lembrado por pelo menos um canal) já foi atingido.

### Por que `fetch` direto (sem SDK do WhatsApp)

A Cloud API do WhatsApp é uma API REST HTTP simples (POST com JSON) — não existe um SDK oficial da Meta pra Node.js que justifique uma dependência nova pra uma única chamada. Mesmo espírito de `src/lib/rate-limit.ts` (código próprio simples em vez de uma lib pra algo pequeno).
