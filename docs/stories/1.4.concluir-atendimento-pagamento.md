## Story

**As a** operador do balcão,
**I want** concluir um atendimento e registrar o pagamento no mesmo passo,
**so that** o caixa reflita a receita real sem etapa separada.

## Acceptance Criteria

1. Na agenda, um agendamento `AGENDADO` tem a ação "Concluir e receber" que abre um diálogo.
2. O diálogo pré-preenche o valor cobrado com o `preco` de tabela do serviço e permite editá-lo.
3. O operador adiciona uma ou mais linhas de pagamento (valor + forma ∈ DINHEIRO/PIX/DEBITO/CREDITO); a soma é exibida e comparada ao valor cobrado.
4. Confirmar com `soma == valorCobrado` grava `Agendamento.valorCobrado`, cria os `Pagamento` e muda o status para `CONCLUIDO`, tudo em uma transação.
5. Se a soma difere do valor cobrado, o sistema bloqueia — exceto a opção explícita "Concluir sem pagamento (cortesia)", que grava `valorCobrado = 0` e nenhum pagamento.
6. Tentar concluir um agendamento que já está `CONCLUIDO` é rejeitado com mensagem clara (idempotência).
7. Erro em qualquer etapa não deixa estado parcial (nenhum `Pagamento` órfão, status inalterado).

## Dev Notes

### Contexto (fonte: `docs/architecture.md#4`, `#5`)

- Contrato da action e regra de validação central estão em arquitetura §4. Resumo:
  ```
  soma = somarPagamentos(pagamentos)
  cortesia  → exige pagamentos vazio → valorCobrado = 0
  normal    → reais(soma) === reais(valorCobrado) senão erro
  já CONCLUIDO → rejeitar
  ```
- `src/lib/financeiro.ts` (Story 1.2) fornece `somarPagamentos`, `reais`, `FORMAS_PAGAMENTO`.
- Padrão de diálogo: `<dialog>` nativo + server action, **sem lib de modal** (arquitetura §5).
  Fallback documentado: página `/atendimento/[id]/concluir` se o `<dialog>` der problema com revalidação.
- Agendamento atual: `src/app/agendamentos/actions.ts` tem `mudarStatus` que hoje aceita `CONCLUIDO` — esta story tira isso de lá.
- `Servico.preco` é `Float`. `Agendamento` já tem relação com `servico`.

### Assunções explícitas

- Pagamento parcial / fiado **não** é suportado no MVP: a soma tem que fechar exatamente (ou cortesia).
- Não há troco/registro de valor recebido em dinheiro maior que o devido — fora de escopo.
- Um atendimento concluído não é editável nesta story (correção = fora de escopo / manual via reabrir caixa na 1.7).

### Edge cases

- `pagamentos` JSON malformado → `{ ok: false, erro: "Dados de pagamento inválidos." }`
- valor de pagamento `<= 0` ou não numérico → erro
- valorCobrado negativo → erro; `0` sem cortesia → erro (use a opção cortesia)

### Testing

- **Unit** (Vitest, em `src/lib/` já coberto pela 1.2) — reforçar caso `reais(0.1+0.2) === reais(0.3)`.
- **Manual:**
  1. Concluir "Corte" (R$ 80) com 1 pagamento PIX 80 → status CONCLUIDO, 1 Pagamento, valorCobrado 80.
  2. Dois pagamentos (50 dinheiro + 30 débito) → conclui.
  3. Soma 70 para cobrado 80 → botão "Confirmar" desabilitado / action recusa.
  4. Cortesia → conclui com valorCobrado 0 e nenhum Pagamento.
  5. Concluir de novo o mesmo → erro de idempotência.
