## Story

**As a** desenvolvedor,
**I want** funções puras para somar pagamentos, calcular fechamento de caixa e comissão,
**so that** a lógica financeira seja determinística e testável isolada do banco.

## Acceptance Criteria

1. `src/lib/financeiro.ts` expõe funções puras: `somarPagamentos`, `totaisPorForma`, `resumoCaixa`, `comissao`, `comissaoPorProfissional`, além dos tipos/constantes `FormaPagamento`, `FORMAS_PAGAMENTO`, `StatusAgendamento`, `STATUS_AGENDAMENTO`.
2. Nenhuma função do módulo importa Prisma, `next/*` ou faz I/O.
3. Existe `reais(n)` documentada como arredondamento para centavos (half-up: `Math.round(n * 100) / 100`); a comissão arredonda apenas o resultado final, não os intermediários.
4. `ticketMedio` retorna `0` quando `qtdAtendimentos === 0` (sem divisão por zero).
5. `src/lib/datas.ts` expõe `inicioDoDia(d)`, `fimDoDia(d)`, `intervaloMes(ref)`, `parseDataParam(s)`, também puras, com premissa de fuso único documentada em comentário.
6. Vitest instalado e configurado; `package.json` ganha `"test": "vitest run"` e `"test:watch": "vitest"`.
7. `src/lib/financeiro.test.ts` e `src/lib/datas.test.ts` cobrem os casos listados em Dev Notes; todos passam.
8. `npm run test`, `npm run lint` e `npm run build` verdes.

## Dev Notes

### Assinaturas alvo (fonte: `docs/architecture.md` §3)

```ts
export type FormaPagamento = "DINHEIRO" | "PIX" | "DEBITO" | "CREDITO";
export const FORMAS_PAGAMENTO: FormaPagamento[] = ["DINHEIRO","PIX","DEBITO","CREDITO"];
export type StatusAgendamento = "AGENDADO" | "CONCLUIDO" | "CANCELADO" | "FALTOU";
export const STATUS_AGENDAMENTO: StatusAgendamento[] = ["AGENDADO","CONCLUIDO","CANCELADO","FALTOU"];

export interface PagamentoInput { valor: number; formaPagamento: FormaPagamento }
export interface AtendimentoInput { valorCobrado: number; profissionalId: string }

export function reais(n: number): number;
export function somarPagamentos(p: PagamentoInput[]): number;
export function totaisPorForma(p: PagamentoInput[]): Record<FormaPagamento, number>;
export function resumoCaixa(pagamentos: PagamentoInput[], qtdAtendimentos: number): {
  porForma: Record<FormaPagamento, number>; totalGeral: number; ticketMedio: number;
};
export function comissao(valorCobrado: number, percentual: number): number;
export function comissaoPorProfissional(
  atendimentos: AtendimentoInput[],
  percentualPorProfissional: Record<string, number>,
): Record<string, { qtd: number; totalCobrado: number; comissao: number }>;
```

### Casos de teste obrigatórios — `financeiro.test.ts` (fonte: arquitetura §3)

- caixa vazio → `totalGeral 0`, `ticketMedio 0`, todas as formas em 0
- 1 forma de pagamento → total correto
- 4 formas de pagamento → `porForma` correto por chave
- atendimento `valorCobrado = 0` → comissão 0
- `comissao(80, 0)` → 0
- `comissao(80, 50)` → 40
- `comissao(80, 33.33)` → 26.66 (conferir half-up)
- `resumoCaixa(..., 0)` → `ticketMedio 0` (sem `NaN`/`Infinity`)
- soma com centavos: `somarPagamentos([{valor:0.1,...},{valor:0.2,...}])` → `0.3` (não `0.30000000000000004`)
- `comissaoPorProfissional` com 2 profissionais e 1 sem atendimento → o sem atendimento aparece com zeros **somente** se estiver em `percentualPorProfissional` (a agregação por si só não inventa profissionais — quem lista todos é a Story 1.8)

### Decisões

- Módulo **puro**: se precisar de tipo do Prisma, redefinir localmente (`PagamentoInput`), não importar `@prisma/client`.
- `datas.ts` criado aqui porque `resumoCaixa`/comissão por período dependem de limites de dia; manter a
  lógica de fuso concentrada e testada evita divergência entre caixa (1.7), painel (1.9) e comissões (1.8).
- Não alterar `src/lib/format.ts` nesta story (labels de forma de pagamento entram na Story 1.4).
