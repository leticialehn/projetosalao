A comparação do Bearer token na Task 5 (`auth !== \`Bearer ${secret}\``) é uma comparação de string comum, não constant-time. Para um endpoint chamado só por um cron autorizado (não um login de usuário final), o risco prático de timing attack é baixo — mas como o próprio template do projeto lista "constant-time comparisons" como foco de Security Stories, registro aqui como melhoria opcional (ex.: `crypto.timingSafeEqual`) que o @dev pode aplicar a critério próprio, sem que isso bloqueie a story. ## Story

**As a** cliente que agendou pelo link público,
**I want** receber um e-mail confirmando meu agendamento e um lembrete antes do horário,
**so that** eu não esqueça o compromisso e o salão tenha menos falta (no-show).

## Acceptance Criteria

1. Nova coluna `Agendamento.lembreteEnviadoEm` (`DateTime?`, migração aditiva, nenhuma coluna existente é alterada) — marca quando o lembrete daquele agendamento já foi enviado, evitando duplicidade.
2. `src/lib/email.ts` expõe `enviarEmail({ to, subject, html }): Promise<boolean>`. Sem `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS`/`EMAIL_FROM` configurados (todas obrigatórias), retorna `false` imediatamente, **sem tentar enviar e sem lançar erro** — recurso desativado, não quebrado (NFR22).
3. Ao confirmar um agendamento público (`criarAgendamentoPublico`, Story 8.1), se houver e-mail disponível (o digitado no formulário, ou — quando o campo veio vazio — o já cadastrado no `Cliente` reaproveitado), um e-mail de confirmação é enviado. Falha no envio (SMTP fora do ar, credencial errada, feature desativada) **não impede nem desfaz** a criação do agendamento — o retorno da action continua `{ ok: true }` (NFR21).
4. Nova rota `GET /api/lembretes` (fora do grupo `(app)`, sem exigir sessão de usuário — protegida por um segredo próprio, não pelo sistema de login): varre agendamentos com `status: "AGENDADO"`, `lembreteEnviadoEm` nulo, `cliente.email` preenchido e `inicio` dentro da janela de antecedência configurada (`LEMBRETE_ANTECEDENCIA_MIN`, em minutos, default 1440 = 24h); para cada um, envia o e-mail de lembrete e grava `lembreteEnviadoEm`.
5. A rota `/api/lembretes` exige o header `Authorization: Bearer <LEMBRETES_CRON_SECRET>`. Sem `LEMBRETES_CRON_SECRET` configurado no ambiente, a rota responde **503** (desativada) para qualquer chamada, em vez de aceitar tudo por omissão. Com o secret configurado, uma chamada sem o header correto responde **401**.
6. Se o envio de um lembrete específico falhar, `lembreteEnviadoEm` **não** é gravado — o agendamento continua elegível e é tentado de novo na próxima execução da rota (retry natural, sem necessidade de fila/job separado).
7. `.env.example` e `DEPLOY.md` documentam as novas variáveis (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`, `LEMBRETES_CRON_SECRET`, `LEMBRETE_ANTECEDENCIA_MIN`) e deixam explícito que **configurar um Cron Job no painel do Railway** para chamar `/api/lembretes` periodicamente (ex.: a cada hora) é um passo manual de infraestrutura, fora do escopo desta story — mesmo padrão já usado no `DEPLOY.md` pros passos manuais de Volume/Variables da Epic 1.
8. `npm run test`, `npm run lint` e `npm run build` continuam verdes.

### Por que uma rota de API (não uma server action) pro lembrete

Server actions só executam em resposta a uma requisição do navegador (form submit, `useActionState`) — não existe "rodar periodicamente" nesse modelo. Como o deploy é um único processo Next.js no Railway (`next start`, sem worker separado, sem fila), a opção sem custo e sem infraestrutura nova é expor um endpoint HTTP comum (`Route Handler` do App Router) que um Cron Job do próprio Railway chama pelo relógio — daí a necessidade de autenticação própria (Bearer secret) no lugar da sessão de usuário, que não existe nesse contexto.

### Por que o secret ausente responde 503 (não 200 silencioso, nem 500)

Combina dois princípios já usados no projeto: "recurso desativado, não quebrado" (NFR22, mesmo espírito do `enviarEmail` retornando `false`) e "falha cedo com mensagem clara" (`src/instrumentation.ts`). Um 503 com mensagem explícita deixa claro, durante a configuração do Railway, que falta uma variável — em vez de um 200 que faz parecer que está tudo certo (mas nunca envia nada) ou um 500 genérico que sugere bug.
