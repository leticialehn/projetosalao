### Decisão do PO sobre "editar serviço/profissional é DONO-only?" (decisão nº 3 do Dev Notes)

**Modelo adotado:** serviço e profissional são **dados mestres do negócio** → **todas** as mutações (criar/editar/excluir) são **DONO-only**. Cliente e o dia-a-dia (agenda, atendimento, caixa do dia) são **operacionais** → BALCÃO. Preço de serviço e ativação de profissional afetam dinheiro e apuração; o balcão de um salão de ≤ 5 pessoas não precisa mexer nisso (o dono está presente).

**As AC 3, 4 e 6 abaixo já refletem essa decisão** (editada pelo @po).

### Não bloqueante (para o @dev)

- **Decisão nº 1 (redirect vs erro em `exigirPapel`):** recomendação do PO — `exigirPapel` lança um erro tipado; wrapper nas actions `{ ok, erro }` converte para `{ ok:false, erro:"Ação permitida apenas para o dono." }`; nas `void` (ex.: `criarServico` via `<form action={...}>`), aceitar o `redirect("/login")` OU um retorno silencioso — padronizar e documentar.
- **Decisão nº 2 (BALCÃO vê `/profissionais`):** aprovado esconder a rota inteira do BALCÃO por ora. Se o balcão precisar consultar telefone de profissional, vira follow-up (`/equipe` read-only).
- **Autenticação de rota:** `/usuarios` e `/profissionais` e `/servicos` devem redirecionar o BALCÃO no `page.tsx` (Server Component com `exigirPapel("DONO")`), não só sumir do `Nav`.

## Story

**As a** dono do salão,
**I want** que o operador de balcão não consiga alterar comissões, taxas ou apagar cadastros,
**so that** mudanças sensíveis (dinheiro e dados mestres) fiquem só comigo.

## Acceptance Criteria

1. `Usuario.papel` já existe (`"DONO" | "BALCAO"`, default `"DONO"` — criado na Story 2.1). Esta story passa a **usar** esse campo para autorizar.
2. Existe uma tela `/usuarios` (**acesso só DONO**) para: listar usuários, criar um novo (usuário + senha + papel), trocar a senha de um usuário e remover um usuário. Não é possível remover o último usuário `DONO` nem rebaixar o último `DONO` para `BALCAO`.
3. **Ações restritas ao DONO** (checagem no servidor, na própria server action — não só escondendo o botão):
   - **todas** as mutações de **serviço**: `criarServico`, `atualizarServico`, `excluirServico`
   - **todas** as mutações de **profissional**: `criarProfissional`, `atualizarProfissional`, `excluirProfissional`, `definirComissao`
   - **excluir cliente** (`excluirCliente`)
   - **reabrir** um caixa já fechado (`reabrirCaixa`)
   - qualquer ação de `/usuarios`
   - as rotas `/servicos`, `/profissionais` e `/usuarios` redirecionam o BALCÃO (guarda `exigirPapel("DONO")` no `page.tsx`)
4. O **BALCÃO** pode: ver e usar a agenda; criar / concluir / remarcar / cancelar / marcar falta em atendimentos; **fechar** o caixa do dia corrente (`fecharCaixa`); ver painel; ver a lista e a ficha de cliente, editar observações, **criar e editar cliente** (`criarCliente`, `atualizarCliente`, `atualizarObservacoesCliente`). Não pode nada do AC 3.
5. Uma ação negada por papel retorna `{ ok: false, erro: "Ação permitida apenas para o dono." }` (ou, nas ações fire-and-forget, não executa e não quebra a tela) — **e a operação não acontece**.
6. O layout esconde do BALCÃO os controles que ele não pode usar: links "Usuários", "Profissionais" e "Serviços" no `Nav`; o botão "Excluir" na lista de clientes; e o botão "Reabrir" no caixa. (As rotas `/servicos` e `/profissionais` já são bloqueadas no servidor pelo AC 3, então a UI dentro delas não precisa de condicional por papel.)
7. A barra lateral mostra o papel do usuário logado ("Dono" / "Balcão") junto do nome.
8. Testes: `exigirPapel` (unit) + pelo menos um teste garantindo que uma server action restrita **rejeita** quando a sessão é de um `BALCAO`. `npm run test`, `npm run lint`, `npm run build` verdes. Sem migração (o campo já existe).

## Dev Notes

### Contexto (Story 2.1)

- `src/lib/sessao.ts`: `exigirSessao()` retorna `{ usuarioId, usuario, papel }` e faz `redirect("/login")` se não houver sessão. `src/lib/sessao-config.ts` tem a config Edge-safe.
- Toda server action mutadora de `(app)` **já chama `await exigirSessao()`** na primeira linha (Story 2.1). Esta story troca essas chamadas por `exigirPapel(...)` onde há restrição, e mantém `exigirSessao()` nas demais.
- `Usuario` model: `id`, `usuario @unique`, `senhaHash`, `papel @default("DONO")`, `criadoEm`. **Sem migração nesta story.**
- `bcryptjs` já é dependência; `bcrypt.hash(senha, 10)` é o padrão (ver `prisma/seed-admin.ts`).
- `Nav.tsx` é `"use client"` (usa `usePathname`); recebe props do layout server.
- Rows (`ServicoRow`, `ProfissionalRow`, `ClienteRow`) são client components renderizados pelas `page.tsx` server.

### Decisões a tomar (registrar no Change Log)

1. **`exigirPapel` — redirect ou erro?** Para ações fire-and-forget (retornam `void`), `redirect("/login")` é abrupto mas simples. Para ações `{ ok, erro }`, melhor retornar o erro e deixar a tela mostrar. Recomendação: `exigirPapel` lança um `ForbiddenError` custom; um pequeno wrapper nas actions `{ ok, erro }` captura e devolve `{ ok:false, erro:"Ação permitida apenas para o dono." }`; nas `void`, deixa propagar (Next mostra erro) OU retorna silenciosamente. Definir e padronizar.
2. **BALCÃO vê `/profissionais`?** A tela mistura dados úteis (telefone, especialidade) com a edição de comissão. Opções: (a) esconder a rota inteira do BALCÃO; (b) mostrar read-only sem o campo de comissão e sem excluir. Recomendação inicial: **(a) esconder** — simples; reabrir como melhoria se o balcão precisar consultar contatos.
3. **Editar serviço/profissional (nome, preço) — DONO-only também?** O PRD lista só *excluir* como restrito. Preço afeta dinheiro. Recomendação: manter conforme PRD (editar = liberado) nesta story e abrir a pergunta para o @po; se ele quiser restringir, é trivial adicionar.

### Assunções explícitas

- RBAC de 2 papéis fixos, sem permissões granulares. `papel` é string (consistente com `status` do Epic 1).
- Sem tela de "meu perfil" / trocar a própria senha nesta story (o DONO troca por `/usuarios`; o BALCÃO pede ao DONO). Pode virar follow-up.
- Esconder controle na UI é conveniência; a verdade é a checagem no servidor (AC 3/5).

### Edge cases

- Último DONO: não pode ser removido nem rebaixado (AC 2).
- BALCÃO acessa `/usuarios` digitando a URL → `exigirPapel("DONO")` redireciona.
- BALCÃO dispara a action restrita direto (POST) → rejeitada no servidor (mesma proteção da Story 2.1, agora com papel).
- Criar usuário com `usuario` já existente → `{ ok:false, erro:"Já existe um usuário com esse nome." }`.

### Testing

- **Unit:** `exigirPapel` (Vitest, com o mesmo mock de sessão de `sessao.test.ts`).
- **Ação restrita:** `definirComissao` com sessão BALCAO → erro/reject, `ComissaoRegra` inalterada.
- **Manual:**
  1. Criar um usuário `caixa1` / papel BALCÃO em `/usuarios` (logado como dono).
  2. Sair, entrar como `caixa1`: `Nav` sem "Usuários"/"Profissionais"; sem botões "Excluir"; sem "Reabrir" no caixa; barra lateral mostra "Balcão".
  3. Como `caixa1`: concluir um atendimento e fechar o caixa do dia → funciona.
  4. Como `caixa1`, abrir `/usuarios` na URL → volta para `/login`.
  5. Tentar remover o único DONO → recusado.
