### Correção crítica aplicada nesta validação (não era mecânica — era uma lacuna real de escopo)

- **AC 7 (nova) + Task 5 (nova) — `excluirProduto` estava desatualizado.** O draft original não previa atualizar `excluirProduto` (Story 3.1), que hoje sempre exclui fisicamente com um comentário no próprio código avisando "nenhuma tabela referencia Produto ainda... isso muda na Story 3.2". Como `MovimentoEstoque` agora referencia `Produto` com `onDelete: Cascade`, excluir um produto com histórico apagaria a auditoria de movimentações junto — violando diretamente o NFR15 (estoque sempre auditável via histórico). Adicionado: `excluirProduto` passa a verificar `movimentoEstoque.count` antes de decidir entre exclusão física e inativação, mesmo padrão condicional de `excluirServico`. Sem essa correção, a story teria sido aceita com uma regressão silenciosa de auditabilidade.

### Observação da PO

A assunção documentada sobre permitir estoque negativo (não bloqueado nesta story) é uma decisão correta — o PRD não define uma regra de reconciliação, e bloquear exigiria inventar uma. Mantida como está, com a ressalva já registrada para revisão futura se o dono achar confuso na prática.

## Story

**As a** dono do salão (e o balcão, para saídas),
**I want** registrar entradas e saídas manuais de estoque de um produto, com quantidade, motivo e data,
**so that** o estoque atual de cada produto reflita a realidade sem eu precisar editá-lo diretamente.

## Acceptance Criteria

1. Novo model `MovimentoEstoque` (`produtoId`, `tipo` — `ENTRADA`|`SAIDA`, `quantidade`, `motivo`, `data`), migração aditiva (NFR14 do PRD): só cria a tabela nova, não altera `Produto` nem nenhuma outra tabela existente.
2. Nova tela `/produtos/[id]` (ficha do produto, protegida — exige sessão, visível para os dois papéis): mostra nome, categoria, unidade, estoque mínimo, estoque atual, e o histórico de movimentações (mais recente primeiro) — mesmo padrão de `/clientes/[id]`.
3. Cada linha de `/produtos` (`ProdutoRow.tsx`) tem o nome como link para `/produtos/[id]` (mesmo padrão de `ClienteRow.tsx`).
4. Formulário "Registrar movimentação" na ficha do produto: tipo (Entrada/Saída), quantidade (número positivo, obrigatório), motivo (texto livre, obrigatório — ex.: "Compra fornecedor X", "Uso em atendimento", "Perda", "Ajuste de contagem"), data (datetime, default agora, editável).
5. Ao registrar uma movimentação, `Produto.estoqueAtual` é atualizado atomicamente na mesma transação que cria o `MovimentoEstoque` (increment para ENTRADA, decrement para SAÍDA) — nunca editado diretamente pelo usuário (NFR15 do PRD). O campo `estoqueAtual` que já existe desde a Story 3.1 finalmente passa a ser escrito, só por aqui.
6. Guarda de papel (FR26 do PRD): `PAPEL_DONO` registra ENTRADA e SAÍDA; `PAPEL_BALCAO` só registra SAÍDA (visualiza a ficha e o histórico normalmente, mas o formulário não oferece a opção "Entrada" quando logado como balcão, e o servidor rejeita se tentarem forçar via request direto). `PAPEL_BALCAO` continua sem poder cadastrar produto novo nem editar estoque mínimo (regra já existente da Story 3.1, intocada).
7. `excluirProduto` (Story 3.1, hoje sempre exclui fisicamente — comentário no próprio código já avisa que isso mudaria nesta story) passa a verificar se o produto tem alguma movimentação associada antes de decidir: sem movimentação → exclusão física (comportamento atual preservado); com movimentação → inativação (`ativo: false`), preservando o histórico — mesmo padrão condicional de `excluirServico`. Sem isso, excluir um produto com histórico apagaria a auditoria via `onDelete: Cascade` da nova tabela, contrariando o NFR15 (estoque auditável).
8. Nenhuma regressão; `npm run test`, `npm run lint` e `npm run build` continuam verdes.

## Dev Notes

### Contexto

- `prisma/schema.prisma`: `Produto.estoqueAtual` já existe desde a Story 3.1, com o comentário explícito "Nasce em 0 e só muda via movimentação de estoque (Story 3.2)". Esta story é quem finalmente escreve nele. `[Source: prisma/schema.prisma]`
- `src/app/(app)/clientes/[id]/page.tsx` é o modelo mais próximo de "ficha de entidade com histórico": busca a entidade + relação, `notFound()` se não existir, cards de resumo no topo, tabela de histórico embaixo. `[Source: src/app/(app)/clientes/[id]/page.tsx]`
- `src/app/(app)/produtos/ProdutoRow.tsx`: hoje o nome do produto é texto puro (`<td>{produto.nome}</td>`), sem link — vira `<Link>` pra `/produtos/[id]`, mesmo padrão de `ClienteRow.tsx` (`<Link href={`/clientes/${c.id}`}>`). `[Source: src/app/(app)/produtos/ProdutoRow.tsx, src/app/(app)/clientes/ClienteRow.tsx]`
- Padrão de guarda assimétrica por tipo de operação (não só por papel) não tem precedente direto no projeto — o mais próximo é a guarda binária DONO/BALCAO já usada em toda action mutadora. Aqui a novidade é: a *ação* (`registrarMovimento`) é chamável pelos dois papéis, mas o *resultado* depende do `tipo` escolhido. Guardar assim: `exigirSessao()` sempre primeiro (ambos os papéis passam), depois `if (tipo === "ENTRADA" && papel !== PAPEL_DONO) return erro` — não usar `exigirPapel(PAPEL_DONO)` no topo da action inteira, que bloquearia SAÍDA do balcão também.
- `FR26` do PRD (Epic 3) é a fonte desta regra assimétrica — não é uma invenção desta story, está explicitamente no requisito: "Balcão pode visualizar o estoque atual e registrar saída (uso/perda), mas não cadastra produto novo nem edita o estoque mínimo".

### Assunção explícita (fora do que o PRD define — registrar para @po avaliar na validação)

- O PRD não diz o que fazer se uma saída deixaria `estoqueAtual` negativo. **Decisão desta story: permitir** (não bloquear) — o estoque atual é só um número de referência, e um valor negativo é um sinal visível de que a contagem física precisa de ajuste, não um erro fatal do sistema. Bloquear exigiria decidir uma regra de negócio (o que fazer quando a contagem física diverge da soma de movimentos) que o PRD não especifica — inventar isso agora seria Article IV. Se o dono achar confuso ver número negativo na prática, uma story de ajuste fica fácil depois.

### Edge cases

- `quantidade` com vírgula decimal (ex.: "1,5") — seguir o mesmo padrão de parsing já usado em `definirComissao`/`ComissaoRegra` (`bruto.replace(",", ".")`) antes de `Number(...)`.
- Produto inativo (`ativo: false`): a ficha `/produtos/[id]` continua acessível e o formulário de movimentação continua funcionando — inativar um produto (Story 3.1) não bloqueia reconciliar o estoque dele antes de zerar de vez.
- `motivo` vazio ou só espaços → rejeitado no servidor (mesmo padrão de validação de campo obrigatório já usado em `criarServico`/`criarProduto`).

### Testing

- **Unit:** ver Task 6 — cobre a guarda assimétrica (AC 6) e a atomicidade do incremento/decremento (AC 5), que são as duas partes com risco real de regressão silenciosa.
- **Manual:** 1) como DONO, abrir a ficha de um produto, registrar uma Entrada de 10 unidades → estoque atual sobe 10, aparece no histórico; 2) registrar uma Saída de 3 → estoque atual desce pra 7; 3) login como BALCAO, abrir a mesma ficha → vê o histórico e o estoque atual, formulário só oferece "Saída".
