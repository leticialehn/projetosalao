## Story

**As a** dono do salão,
**I want** escolher se a comissão incide sobre o valor bruto ou o líquido (após taxa da maquininha),
**so that** eu não pague comissão sobre um dinheiro que a adquirente reteve.

## Acceptance Criteria

1. Configuração única do salão (`Config`, tabela singleton) com `comissaoBase String @default("BRUTO")` (valores válidos: `"BRUTO"` | `"LIQUIDO"`). Migração aditiva (tabela nova; default `"BRUTO"` preserva o comportamento atual de todo mundo).
2. Existe uma forma de o dono editar essa configuração (tela — ver Dev Notes para a decisão de reaproveitar `/taxas` em vez de criar rota nova). Ação restrita a `PAPEL_DONO` no servidor.
3. Quando `comissaoBase = "LIQUIDO"`, o cálculo de comissão de um atendimento usa o **líquido** dos pagamentos daquele atendimento (bruto menos a taxa de cada forma usada — já cobre o caso de pagamento dividido entre formas, já que cada linha de `Pagamento` carrega sua própria taxa). Sem `Pagamento` associado (legado/edge case), cai no bruto (`valorCobrado`) como fallback.
4. `src/lib/financeiro.ts` ganha a função pura que resolve o valor-base de um atendimento (bruto ou líquido, dado `comissaoBase` e as taxas); `comissaoPorProfissionalComServico` (Story 2.4) passa a aceitar a base como parâmetro. Cobertas por testes nos dois modos (incluindo pagamento dividido em 2 formas).
5. `/comissoes` indica no topo do relatório qual base está em uso no período exibido ("Comissão calculada sobre: Bruto" ou "... Líquido").
6. Trocar a configuração afeta só relatórios gerados **depois** — sem recomputar/gravar histórico (mesma limitação já documentada para o percentual geral desde o Epic 1). Documentar isso na tela de configuração.
7. `npm run test`, `npm run lint`, `npm run build` verdes.

## Dev Notes

### Contexto (Stories 1.3, 1.8, 2.3, 2.4)

- `src/lib/financeiro.ts` hoje (pós Story 2.4): `taxaDePagamento(valor, ConfigTaxa)` já existe e é a peça certa pra calcular o líquido de um `Pagamento` (Story 2.3) — **não reinventar**. `comissaoPorProfissionalComServico(atendimentos, regrasPorProfissional)` (Story 2.4) calcula comissão sobre `a.valorCobrado` direto — é essa a linha que precisa passar a considerar a base. `AtendimentoInput` tem `{ valorCobrado, profissionalId, servicoId }`. `[Source: src/lib/financeiro.ts]`
- `prisma/schema.prisma`: não existe nenhum model de configuração única do salão ainda — esta é a primeira tabela desse tipo no projeto. `Pagamento` tem `agendamentoId`, `valor`, `formaPagamento` (uma linha por forma usada num atendimento — confirmado em `src/app/(app)/atendimento/actions.ts`: a soma dos `Pagamento` de um atendimento sempre bate com `Agendamento.valorCobrado`, exceto cortesia que não tem nenhum). `TaxaPagamento` (Story 2.3) tem `formaPagamento @unique, percentual, valorFixo, ativo`. `[Source: prisma/schema.prisma]`
- `src/app/(app)/comissoes/page.tsx` (pós Story 2.4): busca `Agendamento` do período selecionando `profissionalId, servicoId, valorCobrado` — **não** seleciona `pagamentos` ainda; vai precisar incluir `pagamentos: { select: { valor: true, formaPagamento: true } }` na query pra alimentar o cálculo em modo LIQUIDO. `[Source: src/app/(app)/comissoes/page.tsx]`
- `src/app/(app)/taxas/` (Story 2.3): já é uma tela **dono-only** sobre configuração financeira (taxas por forma de pagamento) — candidata natural pra também hospedar o toggle bruto/líquido, evitando inventar uma rota nova só pra 1 campo.

### Decisão a tomar (registrar no Change Log) — onde fica o toggle

Duas opções, ambas técnicamente equivalentes (é 1 select + 1 action):
1. **Reaproveitar `/taxas`** (recomendado): já é a tela de configuração financeira do dono; adiciona 1 seção "Base da comissão" acima ou abaixo da tabela de taxas. Menos rota, menos item de menu.
2. **Rota nova `/configuracoes`**: mais "correto" a longo prazo se o salão for ganhar mais opções globais depois, mas hoje seria uma tela inteira pra 1 campo.

Recomendação do @sm: opção 1 agora; se `Config` crescer noutras stories futuras, extrair pra rota própria nessa hora (YAGNI). Decisão final é do @dev/@po no momento da implementação.

### Padrão de tabela singleton

Não existe precedente no projeto (é a 1ª tabela desse tipo). Sugestão simples pra não introduzir complexidade nova: `id` fixo conhecido (ex.: `"singleton"`), leitura via `prisma.config.findUnique({ where: { id: "singleton" } })` (pode retornar `null` — tratar como `"BRUTO"`), escrita via `upsert` por esse mesmo `id` fixo. Evita lidar com "qual linha é a certa" sem precisar de lógica extra.

### Assunções explícitas

- Uma única configuração pro salão inteiro (sem por-profissional, sem por-período) — é exatamente o que a Story 2.5 do PRD pede; variação mais fina fica pra uma story futura, se pedida.
- "Líquido" aqui é o líquido **da maquininha** (Story 2.3 — `TaxaPagamento`), não o líquido "sobre custo de produto" ou qualquer outro desconto; isso é escopo de outra discussão de produto.
- Trocar a base **não** recalcula `FechamentoCaixa` nem relatórios já fechados — é só o parâmetro que o relatório de comissões usa a partir de agora (AC 6, mesma limitação que o percentual geral já tem desde o Epic 1).

### Edge cases

- `Config` ainda não existe (banco recém-migrado, ninguém trocou a base ainda) → trata como `"BRUTO"` em todo lugar que lê (relatório, testes).
- Atendimento concluído sem nenhum `Pagamento` associado (legado, se existir; cortesia sempre tem `valorCobrado = 0`) → `valorBaseComissao` cai no bruto (que é `0` pra cortesia, então não muda nada).
- Pagamento dividido em 2+ formas com taxas diferentes (ex.: metade dinheiro, metade crédito) → soma os líquidos de cada linha; não precisa de rateio proporcional além disso, porque cada `Pagamento` já tem sua própria forma e taxa.
- `TaxaPagamento` de uma forma usada no atendimento não existe/está inativa → mesmo fallback já usado na Story 2.3 (`SEM_TAXA` — líquido = bruto pra aquela linha).

### Testing

- **Unit:** ver Task 3.
- **Manual:**
  1. Sem mexer na configuração (`Config` default/inexistente): `/comissoes` mostra "Bruto" e os valores batem com o que já existe hoje (regressão).
  2. Trocar pra "Líquido" na tela escolhida (Task 4).
  3. Concluir um atendimento de R$ 100 no crédito (taxa 3,5% + R$0,10 fixo, exemplo do seed da Story 2.3) com comissão geral 40% → comissão esperada sobre R$ 96,40 (líquido), não R$ 100.
  4. Atendimento com pagamento dividido (ex.: R$ 50 dinheiro + R$ 50 crédito) → comissão sobre a soma dos dois líquidos.
  5. `/comissoes` mostra "Comissão calculada sobre: Líquido" no topo.
  6. Voltar pra "Bruto" → relatório volta a bater com o cálculo original.
