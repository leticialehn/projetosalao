## Story

**As a** dono do salão,
**I want** cadastrar os produtos que uso ou revendo, com um estoque mínimo de referência,
**so that** eu tenha uma lista única de produtos em vez de controlar em papel ou planilha.

## Acceptance Criteria

1. Tela `/produtos` (protegida — exige sessão) lista produtos com nome, categoria, unidade de medida, estoque atual e estoque mínimo. Produtos inativos aparecem por último (mesmo padrão de ordenação de `/servicos`: `ativo desc, nome asc`).
2. `PAPEL_DONO` vê e usa os controles de criar/editar/inativar. `PAPEL_BALCAO` acessa a mesma tela em modo somente leitura (sem formulário de novo produto, sem botões de editar/inativar) — mesmo padrão de `podeReabrir`/`podeExcluir` já usado em `/caixa` e `/clientes` (não é uma guarda de página inteira como `/servicos`, que já bloqueia `PAPEL_BALCAO` totalmente).
3. Cadastro de produto: nome (obrigatório), categoria (texto livre, opcional), unidade de medida (texto livre, ex.: "un", "ml", "g" — sem lista fechada nesta fatia), estoque mínimo (número, default 0, não-negativo). Estoque atual **não** é um campo do formulário — nasce em 0 e só muda via movimentação (Story 3.2); isso deve estar refletido no schema (sem campo editável de estoque atual na criação).
4. Edição de produto: mesmos campos do cadastro, exceto estoque atual (que não existe como campo direto — ver AC 3). Produto pode ser inativado (`ativo: false`) em vez de excluído — mesmo padrão de `excluirServico`: se não houver nenhuma movimentação de estoque associada, exclusão física é permitida; se houver, cai para inativação (soft delete).
5. Toda mutação (`criarProduto`, `atualizarProduto`, `inativarProduto`/`excluirProduto`) valida `papel === PAPEL_DONO` no servidor antes de escrever — mesmo padrão de guarda de `servicos/actions.ts` e `profissionais/actions.ts`. Chamada por `PAPEL_BALCAO` é rejeitada silenciosamente (return sem escrita), igual ao padrão existente.
6. `npm run test`, `npm run lint`, `npm run build` verdes.

## Dev Notes

### Contexto (Epic 3, Stories anteriores relevantes: 1.3/2.2/2.3/2.4 pelo padrão de guarda de papel)

- `src/app/(app)/servicos/actions.ts` e `page.tsx` são o modelo mais próximo de CRUD simples com soft-delete: `exigirSessao()` + `if (papel !== PAPEL_DONO) return;` em toda action; `excluirServico` decide entre `delete` físico e `update({ativo:false})` verificando se há uso (`agendamento.count`). `[Source: src/app/(app)/servicos/actions.ts]`
- **Diferença importante desta story em relação a `/servicos`:** `/servicos` bloqueia `PAPEL_BALCAO` na entrada da página inteira via `exigirPapel(PAPEL_DONO)` (redireciona pra `/` se não for dono). `/produtos` **não pode** fazer isso — FR26 do Epic 3 exige que `PAPEL_BALCAO` visualize a lista. O padrão certo é o de `/caixa/page.tsx` e `/clientes/page.tsx`: `exigirSessao()` (sem restrição de papel) + uma flag booleana (`podeReabrir`, `podeExcluir`) calculada a partir de `sessao.papel === PAPEL_DONO` e passada como prop para os componentes que decidem o que renderizar. `[Source: src/app/(app)/caixa/page.tsx, src/app/(app)/clientes/page.tsx]`
- `prisma/schema.prisma`: não existe nenhum model de produto/estoque ainda. Modelos existentes usam `id String @id @default(cuid())` (não singleton) e `ativo Boolean @default(true)` pra soft delete — mesmo padrão de `Servico`/`Profissional`. `[Source: prisma/schema.prisma]`
- `src/lib/sessao.ts` exporta `exigirSessao()`, `exigirPapel(...papeis)`, `PAPEL_DONO`, `PAPEL_BALCAO`. `[Source: src/lib/sessao.ts]`
- `src/components/Nav.tsx`: array `links` com `{ href, label, dono }` — `dono: true` esconde o item do menu pra `PAPEL_BALCAO`. Como `/produtos` deve ser visível pros dois papéis (leitura), o link entra com `dono: false`, igual `/agenda`, `/painel`, `/caixa`. `[Source: src/components/Nav.tsx]`

### Por que `estoqueAtual` já existe na tabela mas não é escrito nesta story

A Story 3.2 (movimentação de estoque) é quem vai escrever em `estoqueAtual`, recalculando a partir do histórico de `MovimentoEstoque` (ainda não criado). Colocar o campo desde já na Story 3.1 evita uma migração adicional só pra adicionar coluna na 3.2, mas a regra de negócio desta story é clara: nenhuma tela ou action da 3.1 escreve nele — ele só existe e fica em 0. Isso está registrado como AC 3/4 pra não ser esquecido durante a implementação ou quebrado por um CodeRabbit "reuse" sugerindo expor o campo no formulário.

### Assunções explícitas

- Unidade de medida é texto livre nesta fatia (sem enum fechado tipo `TaxaPagamento.formaPagamento`) — se o dono pedir consistência (autocomplete, lista fixa), fica pra uma story de refinamento depois que o cadastro estiver em uso real (YAGNI, mesmo raciocínio já usado nas categorias do Epic 2).
- Sem upload de imagem/foto de produto nesta fatia — fora de escopo do Epic 3 como um todo (nem mencionado no PRD).
- Exclusão física só é possível nesta story porque não existe ainda nenhuma tabela que referencie `Produto` (a Story 3.2 introduz `MovimentoEstoque` com FK); depois da 3.2, a mesma lógica condicional de `excluirServico` passa a valer de verdade (hoje sempre cai no ramo "sem uso").

### Edge cases

- Nome vazio ou só espaços → rejeitado no servidor (mesmo padrão de `criarServico`).
- `estoqueMinimo` negativo → rejeitado (`Number.isNaN` ou `< 0`).
- `PAPEL_BALCAO` chamando a action diretamente (fora da UI, ex. DevTools) → guarda no servidor barra, mesmo padrão testado em `profissionais/actions.test.ts`.

### Testing

- **Unit:** ver Task 6 — replica o padrão de `profissionais/actions.test.ts` (guarda de papel) adaptado pra `Produto`.
- **Manual:**
  1. Login como `dono`: abrir `/produtos`, cadastrar um produto (ex.: "Shampoo 1L", categoria "Revenda", unidade "un", estoque mínimo 3) → aparece na lista com estoque atual 0.
  2. Editar o produto (mudar categoria) → lista atualiza.
  3. Inativar → produto some do topo da lista (ordenação `ativo desc`), continua visível no fim se a listagem não filtrar inativos (AC 1 não pede ocultar, só ordenar por último).
  4. Login como usuário `BALCAO`: abrir `/produtos` → vê a lista, **não** vê formulário de novo produto nem botões de editar/inativar.
