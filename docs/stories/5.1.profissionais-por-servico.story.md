## Story

**As a** dono do salão,
**I want** que, ao escolher o serviço na tela de novo agendamento, só apareçam no campo "Profissional" quem realmente faz aquele serviço,
**so that** eu (ou o balcão) não agende por engano um serviço com quem não sabe fazer.

## Acceptance Criteria

1. Novo relacionamento N:N entre `Profissional` e `Servico` (`profissional.servicos` / `servico.profissionais`), migração aditiva (só cria tabela de junção, não altera nenhuma tabela existente).
2. **Comportamento padrão (retrocompatível):** um profissional **sem nenhum serviço vinculado** é tratado como "atende todos os serviços" — não fica subitamente impossível de agendar para ninguém assim que a migração rodar. A restrição só passa a valer para um profissional a partir do momento em que o dono vincula pelo menos um serviço a ele.
3. Tela `/profissionais` (`PAPEL_DONO`, modo de edição já existente por profissional): cada serviço no bloco "Comissão por serviço" ganha um checkbox "Atende" — marcar/desmarcar liga ou desliga o vínculo daquele profissional com aquele serviço. Reaproveita o mesmo formulário/botão "Salvar" já existente por serviço (não cria um botão novo).
4. Tela `/agendamentos`, formulário "Novo agendamento" (`NovoAgendamento.tsx`): ao escolher um serviço no campo "Serviço", o campo "Profissional" passa a listar só quem atende aquele serviço (mais quem não tem nenhum vínculo configurado — regra do AC 2). Antes de escolher um serviço, a lista de profissionais mostra todos (comportamento atual). Se o profissional selecionado deixar de estar na lista filtrada (porque o serviço mudou), a seleção de profissional é limpa.
5. Guarda também no servidor (`criarAgendamento`, em `agendamentos/actions.ts`): se o profissional tiver pelo menos um serviço vinculado e o serviço escolhido não estiver entre eles, a action rejeita com uma mensagem de erro clara — mesmo padrão de validação server-side já usado no restante do projeto (não confiar só no filtro do `<select>` no cliente).
6. Fora de escopo nesta story (documentado, não esquecido): o diálogo de "Remarcar" (`AgendaAcoes.tsx`) e o link "livre +" das colunas da Agenda **não** filtram profissional por serviço — continuam como estão. Fica para uma story futura se o dono sentir falta.
7. Nenhuma regressão; `npm run test`, `npm run lint` e `npm run build` continuam verdes.

## Dev Notes

### Contexto

- Hoje não existe nenhum relacionamento entre `Profissional` e `Servico` no schema — a única ligação indireta é `ComissaoRegra` (`profissionalId` + `servicoId` opcional), mas ela é só uma *regra de comissão*, não indica quem atende o quê. Não reaproveitar `ComissaoRegra` para essa finalidade — são conceitos diferentes (um profissional pode ter uma regra de comissão específica pra um serviço mesmo sem "atender" oficialmente aquele serviço, e vice-versa). `[Source: prisma/schema.prisma]`
- `src/app/(app)/profissionais/ProfissionalRow.tsx` já tem um bloco de edição por serviço (comissão por serviço, Story 1.3/2.4) — é o lugar natural pra pendurar o checkbox "Atende", reaproveitando o mesmo `<form>` por linha de serviço em vez de criar uma seção nova. `[Source: src/app/(app)/profissionais/ProfissionalRow.tsx]`
- `src/app/(app)/agendamentos/NovoAgendamento.tsx` é `"use client"`, mas hoje usa `<select defaultValue>` sem estado controlado — os campos não conversam entre si. Precisa virar controlado no campo `servicoId` pra poder filtrar `profissionalId` reativamente. `[Source: src/app/(app)/agendamentos/NovoAgendamento.tsx]`
- `src/app/(app)/agendamentos/actions.ts`: `criarAgendamento` já busca o `servico` pra calcular o horário de fim e checa conflito de agenda (`temConflito`) — o novo check de "profissional atende esse serviço" entra logo depois de buscar o `servico`, antes de checar conflito (falha rápida, evita fazer trabalho desnecessário se a combinação já é inválida). `[Source: src/app/(app)/agendamentos/actions.ts]`

### Edge cases

- Profissional com vínculo a **todos** os serviços ativos (marcou "Atende" em cada um manualmente) se comporta de forma idêntica a um profissional sem nenhum vínculo (aparece pra tudo) — são caminhos de código diferentes (lista com todos os IDs vs. lista vazia) mas o resultado observável é o mesmo. Não precisa de tratamento especial.
- Serviço inativado (`ativo: false`) depois que já tinha profissionais vinculados: o vínculo continua existindo no banco, mas o serviço já não aparece no `<select>` de `/agendamentos` (que já filtra `ativo: true`) nem na lista de checkboxes de `/profissionais` (mesma query com `where: { ativo: true }`) — nada a fazer aqui, o filtro de `ativo` já resolve.
- Trocar de serviço no formulário depois de já ter escolhido um profissional válido: se o novo serviço também for atendido por esse profissional, a seleção **não** precisa ser limpa (evita frustração de perder a escolha à toa).

### Testing

- **Unit:** ver Task 5 — cobre exatamente a regra de retrocompatibilidade (AC 2) e a guarda server-side (AC 5), que são as duas partes com risco real de regressão silenciosa.
- **Manual:** 1) cadastrar um profissional novo, marcar "Atende" só em "Corte feminino"; 2) abrir `/agendamentos`, escolher "Corte feminino" → esse profissional aparece; escolher "Manicure" → esse profissional some da lista; 3) conferir que os profissionais do seed (Ana/Bruno/Carla, sem nenhum vínculo configurado ainda) continuam aparecendo pra qualquer serviço.
