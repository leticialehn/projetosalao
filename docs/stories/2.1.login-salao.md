## Story

**As a** dono do salão,
**I want** proteger o acesso ao sistema com um login,
**so that** os dados do salão (clientes, telefones, faturamento, comissões) não fiquem abertos a quem tiver o link.

## Acceptance Criteria

1. Existe a rota `/login` com formulário (usuário + senha), acessível sem sessão; é a única rota (além de assets estáticos) fora da área protegida nesta story.
2. Qualquer outra rota, acessada sem sessão válida, redireciona para `/login`. A checagem é feita em um único ponto (middleware ou guarda em layout de servidor), não repetida em cada página.
3. A credencial do "dono" é criada por um comando de seed que grava um registro `Usuario` com a senha em **hash** (bcrypt). O usuário e a senha inicial vêm de variáveis de ambiente (`ADMIN_USER`, `ADMIN_PASSWORD`); nunca há senha em texto puro no repositório nem no banco.
4. A sessão é mantida por **cookie HTTP-only, assinado/criptografado**; a chave vem da variável de ambiente `SESSION_SECRET` (mín. 32 caracteres). O app não sobe sem `SESSION_SECRET` definido.
5. Há ação **"Sair"** visível no layout (na barra lateral) que encerra a sessão e leva a `/login`.
6. A sessão expira após período de inatividade configurável, default **12 horas** (`SESSION_TTL_HOURS`).
7. Login inválido retorna mensagem **genérica** em pt-BR ("Usuário ou senha inválidos.") — sem revelar qual campo falhou e sem diferença de tempo perceptível entre "usuário não existe" e "senha errada".
8. `npm run build`, `npm run lint`, o typecheck e `npm run test` passam. A migração que cria `Usuario` é não destrutiva (tabela nova; nenhum dado existente afetado).
9. Após login bem-sucedido, o usuário é levado para `/` (agenda). Acessar `/login` já autenticado redireciona para `/`.
10. `DEPLOY.md` e `.env.example` são atualizados com as novas variáveis (`ADMIN_USER`, `ADMIN_PASSWORD`, `SESSION_SECRET`, `SESSION_TTL_HOURS`) e o passo de rodar o seed do usuário uma vez em produção.

### Decisões a tomar (registrar a escolha no Change Log)

1. **Biblioteca de sessão.** Recomendação: `iron-session` v8 — cookie criptografado, API simples,
   funciona em server actions e (v8) em middleware. Alternativa sem dep nova: assinar um JSON com
   `jose` (JWT HS256). `iron-session` é menos código e menos chance de erro. **Peso:** +1 dep pequena.
2. **Hash de senha.** `bcryptjs` (JS puro, sem build nativo — importante no Railway e no Windows).
   Cost 10. Evitar `bcrypt` nativo e `argon2` nativo aqui.
3. **Ponto de proteção.** Preferir `src/middleware.ts` (redireciona antes de renderizar). Se o
   runtime Edge do middleware conflitar com a leitura do cookie da lib escolhida, usar guarda no
   layout do route group `(app)`. Testar as duas rotas: `/` e uma rota de API/ação.
4. **Credencial: env + seed vs. só env.** Escolhido: **entidade `Usuario` + seed** (AC 3), porque a
   Story 2.2 precisa de `Usuario.papel` de qualquer forma. Fazer a migração agora evita retrabalho.

### Assunções explícitas

- Um único usuário (o dono) nesta story. Cadastro de mais usuários / troca de senha pela UI = Story
  2.2 ou posterior. Trocar a senha agora = rodar `db:seed:admin` de novo com `ADMIN_PASSWORD` novo.
- Sem "lembrar-me", sem recuperação de senha por e-mail, sem 2FA no Epic 2.
- Sem rate limiting / bloqueio por tentativas nesta story (salão pequeno, superfície pequena) —
  registrar como possível débito se a URL for muito exposta.
- O agendamento online público (fase 3) terá sua própria rota fora da proteção; não é problema desta
  story, mas o `matcher` do middleware deve ser fácil de estender.

### Edge cases

- `SESSION_SECRET` ausente → app não sobe, erro claro no log (não "funcionar sem proteger").
- Cookie adulterado/expirado → tratado como sem sessão → redirect para `/login`.
- Usuário acessa `/login` já logado → redirect para `/`.
- Deep link para `/caixa?data=...` sem sessão → após login, pode ir direto para `/` (não é
  obrigatório preservar o destino nesta story; se for trivial com o middleware, preservar via
  `?next=`).

### Issues

**H1 — HIGH / security — Server actions não verificam a sessão**
As 6 actions de escrita (`agendamentos`, `atendimento`, `caixa`, `clientes`, `profissionais`, `servicos`) não chamam `lerSessao()`. A proteção hoje é:
- **middleware** — só checa *presença* do cookie (`req.cookies.has`), não a validade; e é contornável por header (CVE-2025-29927, Next 15.1.3);
- **guarda no `(app)/layout.tsx`** — roda no *render* da página; numa invocação de server action a função da action executa **antes** do re-render que dispara o `redirect`.

Resultado: um POST same-origin com um cookie `salao_sessao` qualquer (não vazio) + um action id (extraível dos chunks JS, que são públicos) pode, em tese, alcançar a mutação antes do redirect. Não é trivial de explorar (o CSRF nativo do Next exige `Origin==Host`), mas numa story cujo objetivo é controle de acesso isso não pode ficar aberto — e todas as stories seguintes herdam o padrão.

**Correção pedida (escopo fechado):**
1. Em `src/lib/sessao.ts`, adicionar `exigirSessao()` que faz `lerSessao()` e, se `!usuarioId`, lança / `redirect("/login")`.
2. Chamar `await exigirSessao()` na primeira linha de **toda** server action mutadora do `(app)` (as 6 acima). `entrar`/`sair` ficam de fora.
3. (Opcional, recomendado) no `middleware.ts`, para métodos não-GET, validar o cookie de fato (unseal) em vez de só checar presença — ou ao menos rejeitar cookie malformado.
4. Adicionar 1 teste garantindo que uma action mutadora rejeita quando não há sessão.

**M1 — MEDIUM / requirements — AC4 "app não sobe sem SESSION_SECRET" é só em runtime**
`segredo()` só lança quando `lerSessao()` é chamado (primeiro request), não no boot/build. Na prática o app fica inutilizável sem a variável (todo request erra), mas não "falha ao subir" como o AC diz. Aceitável, mas registrar; se quiser cumprir à risca, validar `process.env.SESSION_SECRET` também em `next.config` ou num `instrumentation.ts`.

**M2 — MEDIUM / requirements — AC6 expiração é absoluta, não por inatividade**
`iron-session` `ttl`/`maxAge` expira 12 h **após o login**, não após a última atividade. O AC pede "inatividade". Para sliding session seria preciso re-salvar a sessão a cada request (ex.: no `(app)/layout.tsx`). Decidir: aceitar expiração absoluta (documentar a mudança de AC) ou implementar o refresh.

**L1 — LOW / security — sem rate limiting**
Já previsto como possível débito na story. OK para agora; revisitar se a URL for muito exposta.

**L2 — LOW / deps — Next 15.1.3 com CVEs conhecidas**
O `npm audit` lista várias (incl. a de middleware). Não bloqueia esta story (a correção H1 remove a dependência do middleware para segurança), mas abrir um chore para subir ao último 15.x.

### Veredito
